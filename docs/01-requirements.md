**Версия 1.0 от 03.11.2026. Автор: Шурман А. Р. ЛР2, ветка lab-2.**
Статус: подготовлено для внешнего ревью, одобрение ещё не получено. Исходная ревизия приложения — e5e60233 (lab-1). FR-n обозначает функцию, NFR-n — проверяемое ограничение, US-n — сценарий. Номера не меняются до конца семестра. Обозначение US используется согласно заданию ЛР2 вместо предварительно упомянутого в ЛР1 UR.

## 1. О приложении

### Назначение и существующие возможности

YogaVibe помогает найти ментора по йоге, изучить профиль, записаться на занятие и вести личные заметки. Ментор ведёт профиль и обрабатывает записи, администратор поддерживает каталог и учётные записи. Проект собственный, работа индивидуальная. См. [паспорт](00-project.md).

На момент начала ЛР2 в коде существуют регистрация/вход, каталог с фильтрами, профили, создание/отмена бронирований, заметки, файлы профилей, кабинеты ментора и администратора. SQLite хранит записи, local-провайдер — файлы. S3/MinIO и OpenWeather — необязательные интеграции. Доступность MinIO не подтверждена, см. issue №5. Результаты ЛР1 не означают приёмку всех требований ЛР2.

В объём семестра входят FR-1–FR-10 и NFR-1–NFR-5. Оплата, видеосвязь, мобильное приложение, восстановление пароля по почте, развитие погоды и промышленная отказоустойчивость исключены. Загрузка вложений ограничена профилями пользователя/ментора; поля связей с заметками/бронированиями существуют в модели, но интерфейс их загрузки этой версией не обещается.

### Роли

| Роль | Права в выбранном объёме |
| --- | --- |
| Гость | Регистрация и вход; каталог требует авторизации |
| Пользователь (user) | Каталог, свои записи, заметки, профиль и файлы |
| Ментор (mentor) | Свой профиль/файлы, записи к себе и завершение занятий |
| Администратор (admin) | Каталог, управление пользователями/менторами и сводка; доступ к файлам по текущей модели прав |

Роль mentor не наследует все права user: API каталога разрешён user/admin, личных заметок и записей — user. Назначение роли mentor и создание профиля Mentor — отдельные действия администратора.

### Термины

| Термин | Значение |
| --- | --- |
| Пользователь / User | Учётная запись с username, email, ролью и активностью; «пользователь» в FR означает user, если другие роли не перечислены |
| Ментор / Mentor | Профиль наставника, связанный с одной User; описание, город, стиль йоги и часовая цена |
| Бронирование / Booking | Запись пользователя к ментору на дату/время и длительность; статусы active, cancelled, completed |
| Заметка / Note | Личный текст длиной 1–1000 символов после удаления крайних пробелов |
| Файловое вложение / FileAttachment | Метаданные файла, загрузившая User и привязка к владельцу; содержимое хранится отдельно |
| Доступный ментор | Mentor с is_available=true; это доступность профиля, а не расписание свободных интервалов |
| Интервал занятия | Полуоткрытый интервал [начало, начало + длительность); соседние занятия не пересекаются |
| Версия записи | updated_at либо created_at, используемая при обнаружении устаревшего редактирования |

RefreshToken — техническая сущность, вне пяти предметных сущностей модели. Даты API передаются с часовым поясом, интерфейс показывает Москву. Цена — целое число рублей. Стоимость = часовая цена × длительность в часах, округлённая вверх; 90 минут оплачиваются как два часа.

## 2. Требования к функционалу

### Приоритеты и состояния

Приоритеты: **обязательно в этом семестре**, **желательно**, **потом**. Желательные функции проверяются после обязательных; «потом» не входит в объём этой версии.
Состояния: **уже есть** — реализация обнаружена в коде в описанной границе, но полная приёмка ещё может требоваться; **нужно доработать** — есть конкретный разрыв с целевым поведением; **нужно сделать** — реализации нет. Все выбранные FR уже представлены в проекте, поэтому новые функции не добавляются искусственно.

### Текущее и планируемое поведение

- **FR-4:** crud.py проверяет одинаковое время начала, а не пересечение интервалов. Защита от гонки не подтверждена ([issue №3](https://github.com/wixucys/yogavibe/issues/3)). cancel_booking запрещает только повторную отмену, поэтому допускает completed → cancelled. Планируются интервальная проверка, защита одновременной записи и запрет отмены завершённой записи.
- **FR-5:** сервер запрещает пустой текст, но handleAddNote в интерфейсе молча прекращает добавление. Планируется видимое сообщение. expected_updated_at уже проверяется сервером; конфликт двух редакторов требует сквозной приёмки.
- **FR-7:** состояние относится к local-провайдеру и профилям; реальный S3 и восстановление файлов не объявляются проверенными.
- Остальные состояния основаны на чтении перечисленных модулей, а не на новом полном приёмочном прогоне ЛР2.

## 3. Пользовательские сценарии

Сценарии описывают целевые требования. Три ключевых сценария имеют конкретные примеры и ошибки. Данные синтетические. ID 7, 12, 42 — подготовленный тестовый набор, а не обещанные ID пустой БД. Для дат часы стенда фиксируются на 03.11.2026 12:00 UTC.

### US-1 — регистрация и вход (FR-1)

**Я как гость** имею уникальные имя/email и пароль, заполняю регистрацию, подтверждаю пароль, отправляю форму, выхожу и вхожу с теми же данными, получаю кабинет активной User с ролью user.

- Вход: username, email, password, confirmPassword; имя/email ещё не заняты.
- Шаги: открыть регистрацию → заполнить поля → отправить → открыть кабинет → выйти → войти по имени или email и паролю.
- Выход: одна User и авторизованный кабинет; повторный вход не создаёт User. confirmPassword проверяется формой и не хранится.
- Пример: anna_yoga, anna.yoga@example.com, пароль/подтверждение YogaStudy2026!. Ожидание: username=anna_yoga, email=anna.yoga@example.com, role=user, is_active=true; переход в /mentors; пароль отсутствует в ответе.
- Ошибка: email anna.yoga.example.com без @ → **«Введите корректный email»**, форма не отправляет запрос, User не создаётся. Пустой password → **«Введите пароль»** с теми же последствиями. Это текущие сообщения формы; прямой API-запрос с неверной схемой возвращает 422.

### US-2 — поиск ментора (FR-2)

**Я как пользователь или администратор** имею активную сессию и критерии поиска, открываю каталог, выбираю город/стиль, получаю подходящих доступных менторов.

- Вход: user/admin, JWT, необязательные город и стиль.
- Шаги: открыть каталог → выбрать город → стиль → дождаться фильтрации → при необходимости сбросить фильтры.
- Выход: соответствующие карточки или пустой результат; данные не изменяются, пустая БД допустима.

### US-3 — карточка ментора (FR-3)

**Я как пользователь или администратор** имею выбранную карточку, открываю её, получаю сведения для решения о записи.

- Вход: сессия user/admin, ID Mentor.
- Шаги: выбрать карточку → открыть → просмотреть описание, город, стиль, опыт и цену.
- Выход: данные выбранного Mentor; неизвестный ID даёт сообщение об отсутствии профиля, записи не создаются.

### US-4 — запись и отмена (FR-4)

**Я как пользователь** имею активную сессию, доступного ментора и свободный будущий интервал, выбираю время/длительность, подтверждаю запись, получаю бронирование и могу отменить его, пока оно активно.

- Вход: user.id=12, mentor.id=7, is_available=true, price=1500; дата с часовым поясом, длительность, тип и необязательный комментарий.
- Шаги: открыть ментора → выбрать время/длительность → подтвердить → открыть «Мои записи» → при необходимости отменить → обновить список.
- Выход: Booking связан с User 12 и Mentor 7; сначала active, при допустимой отмене cancelled; другие записи не меняются.
- Пример: session_date=2026-11-10T15:00:00+03:00, duration_minutes=90, session_type=individual, notes=Первое занятие; интервал свободен. Ожидание: одна active-запись, **3000 ₽**, **10.11.2026 15:00 МСК**, **90 минут**. После отмены именно она cancelled, интервал свободен.
- Неверная дата: прямой API-запрос с 2026-11-01T15:00:00+03:00 при фиксированных часах → HTTP 400, detail **«Дата и время сессии должны быть в будущем»**, Booking не создаётся. Это текущий серверный ответ; форма может отклонить дату раньше.
- Занятость: уже есть active-запись на 15:00–16:30, запрос на 16:00–17:00 → целевой HTTP 409 и видимое **«На выбранное время уже есть запись. Выберите другой интервал»**; новая запись не создаётся. Это доработка: сейчас проверяется только равное начало, создание возвращает 400 с «На это время уже есть бронирование».
- Неполный ввод: нет даты → целевое **«Выберите дату и время занятия»**, запрос не отправляется; формулировка подлежит унификации.
- Два одновременных пересекающихся запроса должны дать одну запись и один отказ. Отмена completed должна отказать, сохранив completed. Эти гарантии планируются.

### US-5 — личная заметка (FR-5)

**Я как пользователь** имею сессию и текст о практике, создаю заметку, проверяю после обновления, редактирую и удаляю, получаю актуальный личный список.

- Вход: user.id=12, текст; при редактировании — ID и версия Note.
- Шаги: открыть «Заметки» → ввести текст → сохранить → обновить → изменить → сохранить → удалить.
- Выход: Note принадлежит User 12; изменения сохраняются, удалённая заметка не возвращается.
- Пример: «  Практика хатха-йоги 30 минут  » → **«Практика хатха-йоги 30 минут»** без крайних пробелов, user_id=12. Замена на «Практика хатха-йоги 40 минут» меняет ту же Note; удаление убирает её из списка. ID/timestamp генерируются.
- Неверный ввод: три пробела → целевое видимое **«Текст заметки не может быть пустым»**, Note не создаётся. Сейчас форма молча прекращает добавление; прямой API-запрос возвращает 422 с этой причиной. UI отмечен как доработка.
- Конфликт: два редактора открыли Note 42 одной версии; первый сохранил, второй отправил старый expected_updated_at → HTTP 409, **«Запись была изменена. Обновите страницу и повторите действие»**; текст первого не меняется. Серверная проверка и перевод сообщения NotesService существуют, сквозная приёмка планируется.

### US-6 — изменение профиля (FR-6)

**Я как пользователь** имею сессию и сведения о себе, открываю анкету, изменяю поля и сохраняю, получаю обновлённый профиль.

- Вход: city, yoga_style, experience, goals; необязательные поля можно очистить.
- Шаги: открыть анкету → изменить → сохранить → повторно открыть.
- Выход: новые значения своей User; роль и чужие профили не меняются.

### US-7 — файлы профиля (FR-7)

**Я как пользователь или ментор** имею свой профиль и допустимый файл, загружаю его в разрешённую категорию, скачиваю и при необходимости удаляю, получаю управляемое вложение профиля.

- Вход: JWT, свой профиль, имя/тип/содержимое/категория, размер 1–10 485 760 байт. Аватар: JPG/PNG/GIF/WebP; документы: эти форматы или PDF.
- Шаги: открыть профиль → выбрать категорию/файл → загрузить → получить ссылку → скачать → удалить.
- Выход: FileAttachment и содержимое в хранилище, временная ссылка; после удаления файл недоступен. Неверный тип/размер не создаёт вложение. Доступ admin — исключение NFR-3.

### US-8 — работа ментора (FR-8)

**Я как ментор** имею свой Mentor и активные записи к себе, меняю описание профиля, открываю записи и отмечаю занятие завершённым, получаю актуальные профиль и состояние занятия.

- Вход: mentor, свой профиль, новое описание/город/цена, ID своей active-записи.
- Шаги: открыть кабинет → сохранить профиль → открыть записи → выбрать активную → завершить → обновить.
- Выход: изменения своего Mentor; Booking имеет completed. Чужая запись → 403 без изменения. Текущий API не проверяет время окончания, запрет раннего завершения не входит в v1.0.

### US-9 — управление пользователями (FR-9)

**Я как администратор** имею список User, выбираю запись и меняю роль/активность, получаю обновлённые права учётной записи.

- Вход: admin, ID User, role=user/mentor/admin или is_active.
- Шаги: открыть пользователей → выбрать → изменить → сохранить → обновить.
- Выход: новые права/активность; попытка деактивировать или понизить последнего администратора отклоняется. Существующий Mentor при смене роли требует согласованного административного решения.

### US-10 — каталог и сводка (FR-10)

**Я как администратор** имею User с ролью mentor без профиля, создаю профиль, меняю цену и открываю сводку, получаю обновлённый каталог и показатели.

- Вход: ID User, имя, описание, пол, город, цена, стиль; контрольный набор данных для сводки.
- Шаги: создать Mentor → найти → изменить цену/доступность → открыть каталог → сводку.
- Выход: один Mentor для одной User, новые поля и правильные счётчики. Неизвестная User, роль не mentor или повторный профиль дают отказ без дубля.

В контексте интерфейс, API, SQLite и локальные файлы находятся внутри границы YogaVibe. S3 и OpenWeather — внешние необязательные интеграции. Платежей, почтового сервиса и очередей в выбранном объёме нет.

Варианты использования изображены Mermaid flowchart с овальными узлами: это представление use-case модели, не отдельная UML-грамматика. Ролевые ограничения раздела 1 сохраняются.

Модель данных показывает nullable-связи FileAttachment с User/Mentor/Booking/Note и обязательную связь загрузившей User. Предполагается ровно один владелец вложения, но SQL CHECK сейчас не заявляется; загрузка сервисом ограничена профилями. Обратные avatar_file_id/photo_file_id выбирают аватар из вложений и опущены ради читаемости. RefreshToken — техническая таблица вне модели.

Состояния отражают целевой цикл: запись сразу active, состояний pending/paid нет. Отменённая/завершённая запись остаётся в истории, возврата в active нет. Физическое удаление существующим API — операция хранения вне бизнес-цикла. Текущий дефект completed → cancelled описан в разделе 2, в целевой модели такого перехода нет.

### Контроль полноты и ревью

Подготовлены 10 FR, 5 NFR, 10 US, три конкретных примера с ошибками и семь моделей. Каждый FR имеет US, каждый US ссылается на FR. Статусы сверены с кодом; цели и подтверждённое поведение разделены. Нагрузочные измерения, восстановление и одобрение рецензента не заявляются.

На ревью нужно проверить: интервал и финальные статусы FR-4; пустую заметку FR-5; доступ admin к файлам NFR-3; стенд NFR-2 и восстановление NFR-4. До согласования это конкретный проект требований.

Работа индивидуальная. По задаче 4 рецензент — студент другой команды по назначению преподавателя; пока не назначен. Он оставляет содержательное замечание к месту PR, автор отвечает отдельным исправляющим коммитом или обоснованием, затем обсуждение разрешается. Слияние и тег lab-2 — после approve. Самопроверка не заменяет внешнее ревью. PR ЛР1 №6 пока открыт: PR ЛР2 в main временно включает базовые изменения ЛР1, что отмечается в его описании.
