## 2. Условия и входные данные

Нужны работающие API и база данных, активная учётная запись с ролью **user** и действующий access token этой записи. Роли mentor/admin сами по себе не дают доступ к заметкам. Владельца сервер определяет по токену; передавать user_id не требуется.

| Элемент запроса | Тип | Обязательность | Значение / ограничение |
| --- | --- | --- | --- |
| Метод и путь | HTTP | Да | POST /api/v1/notes, без параметров пути и query |
| Authorization | Заголовок | Да | Bearer ACCESS_TOKEN, где ACCESS_TOKEN — access_token из входа или регистрации |
| Content-Type | Заголовок | Да | application/json |
| Тело | JSON-объект | Да | Объект с полем text |
| text | Строка | Да | От 1 до 1000 символов после удаления пробельных символов по краям методом strip(); длина считается как Python len(str), а не байты UTF-8 |

Переводы строк внутри текста сохраняются. Отсутствие text, null, значение другого типа или недопустимая длина приводят к 422. Дополнительные поля текущая схема игнорирует: они не позволяют назначить владельца или ID. Клиенту следует отправлять только text.

Операция не идемпотентна: два успешных одинаковых запроса создадут две заметки. Автоматический повтор после сетевого обрыва может создать дубликат.

### Подготовка токена для примеров

Зарегистрируйте обычного пользователя в интерфейсе. Затем выполните вход с его логином/email и паролем (значения ниже демонстрационные; используйте данные своей тестовой записи):

```bash
curl -sS -X POST http://localhost/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  --data '{"login":"anna_yoga","password":"YogaStudy2026!"}'
```

Из успешного JSON-ответа скопируйте поле access_token целиком в переменную своей оболочки:

```bash
TOKEN='вставьте_access_token_из_ответа'
```

Это заменяемое значение, а не готовый токен. Не публикуйте реальный токен в репозитории. Примеры ниже рассчитаны на bash/zsh и UTF-8.

## 3. Успешный результат

**HTTP 200 OK**, Content-Type: application/json. Сервер сохраняет одну заметку в БД до отправки ответа.

| Поле ответа | Тип | Значение |
| --- | --- | --- |
| id | Целое число | Сгенерированный положительный идентификатор заметки |
| user_id | Целое число | Идентификатор пользователя из токена |
| text | Строка | Сохранённый текст без пробельных символов по краям |
| created_at | Строка даты ISO 8601 | Время создания с часовым поясом +03:00 |
| updated_at | Строка даты ISO 8601 или null | При создании null; появляется после изменения |

### Пример 1: создание заметки

```bash
curl -i -X POST http://localhost/api/v1/notes \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  --data '{"text":"  После занятия: 10 минут дыхательной практики.  "}'
```

Ожидается HTTP 200 и объект следующего вида:

```json
{
  "id": 2,
  "user_id": 12,
  "text": "После занятия: 10 минут дыхательной практики.",
  "created_at": "2026-11-16T22:13:43+03:00",
  "updated_at": null
}
```

ID и дата показаны по фактическому пробному вызову; при повторении они будут другими. user_id должен соответствовать вашей учётной записи. Сохранённую заметку можно проверить запросом GET /api/v1/notes/{id} с тем же Authorization. После проверки её можно удалить DELETE-запросом по тому же пути.

## 4. Характерная ошибка: пустой текст

При корректной авторизации, но text из одних пробелов сервер отвечает **HTTP 422 Unprocessable Entity**, Content-Type: application/json. Заметка не создаётся; число записей не меняется.

### Пример 2: отклонение пустой заметки

```bash
curl -i -X POST http://localhost/api/v1/notes \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  --data '{"text":"   "}'
```

Ожидаемый ответ текущей версии зависимостей:

```json
{
  "detail": [
    {
      "type": "value_error",
      "loc": ["body", "text"],
      "msg": "Value error, Текст заметки не может быть пустым",
      "input": "   ",
      "ctx": {"error": {}},
      "url": "https://errors.pydantic.dev/2.5/v/value_error"
    }
  ]
}
```

Клиент распознаёт ошибку по HTTP 422 и элементу detail с loc = ["body", "text"]. Поле msg объясняет причину. Диагностические ctx/url не следует использовать для бизнес-логики. Это ответ валидации FastAPI; он отличается от обёртки status/error/detail/path для HTTPException.

При отсутствии Authorization текущая версия возвращает 403; недействительный/истёкший токен — 401; неподходящая роль — 403. Поэтому для воспроизведения именно ошибки text сначала нужен действующий токен пользователя.
